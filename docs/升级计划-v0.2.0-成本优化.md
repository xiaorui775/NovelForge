# NovelForge 低成本优化升级计划

> **目标用户**: 个人创作者，自托管，低成本运行
> **约束条件**: 架构不改（保持单进程 FastAPI + 进程内任务）、不考虑手机端
> **核心目标**: 降低 API 调用成本、减少 token 浪费、提升单次生成性价比
> **版本**: v0.2.0 成本优化专项

---

## 0. 背景与目标

### 0.1 当前痛点

| 痛点 | 典型场景 | 成本影响 |
|-----|---------|---------|
| 模型选择单一 | 所有任务都用同一模型，无法利用国产模型低价 | 简单任务成本高 3-5 倍 |
| 上下文过度加载 | 续写第 50 章时加载全部前章摘要 | 浪费 40-60% token |
| 中断即重来 | 生成中途断线，全部重新生成 | 浪费 50-80% 已生成 token |
| JSON 解析失败重试 | AI 返回格式不稳定，多次重试 | 每次重试浪费 500-2000 token |
| 缺乏成本感知 | 用户不知道本次生成花了多少钱 | 无法主动优化 |

### 0.2 核心指标

| 指标 | 当前 | 目标 | 测量方式 |
|-----|------|------|---------|
| 平均单章生成成本 | 基准 | ↓ 40-60% | 按项目统计费用 |
| 上下文 token 利用率 | 低 | ↑ 2-3 倍 | 输入/产出 token 比 |
| 中断恢复成本 | 100% 重来 | ↓ 70% | 断点续传节省量 |
| 格式错误重试率 | 15-30% | < 5% | 日志统计 |

## 1. 升级范围（严格限定）

### ✅ 包含

- 多模型适配器扩展（OpenAI 兼容的国产模型）
- 现有服务层逻辑优化（上下文构建、缓存、成本控制）
- 前端配置与展示增强（成本标签、模型选择、限制设置）
- 提示词模板补充（成本分级版本）
- 数据统计与历史记录（已有数据，补展示）

### ❌ 不包含

- 架构重构（不引入 Celery/Redis，不拆分服务）
- 新功能模块（不加协作、社区、插件等）
- 手机端适配
- 深度 AI 能力（不做风格学习、语义搜索等）
- 测试补全（本次专注成本优化，测试另起计划）

## 2. 开发计划

### Phase 1: 多模型支持与路由（Week 1-2）

#### 1.1 扩展模型适配器

**目标**: 支持至少 3 个主流国产/低价模型

| 模型 | 供应商 | 价格优势 | 备注 |
|-----|-------|---------|------|
| DeepSeek-V3 | DeepSeek | 极低（约 GPT-4 的 1/20） | 推荐默认 |
| 通义千问-Turbo | 阿里云 | 低 | 中文能力强 |
| 智谱 GLM-4 | 智谱 AI | 中 | 推理能力好 |

**交付物**:
- [ ] `backend/app/adapters/` 新增适配器
  - `deepseek_adapter.py`（或统一 OpenAI 兼容适配器参数化）
  - `qwen_adapter.py`
  - `glm_adapter.py`
- [ ] `adapter_factory.py` 注册新 provider
- [ ] `backend/app/schemas/model_config.py` 补充 `provider` 枚举值
- [ ] 模型配置页面支持选择 provider（前端已有，验证兼容性）

**验收标准**:
- 3 个新模型可在模型配置页面添加并测试连接成功
- 生成/续写/改写功能可用
- token 计数与费用估算正确（基于模型配置的单价）

---

#### 1.2 任务-模型路由策略

**目标**: 根据任务类型自动/手动选择合适模型

**路由维度**（按优先级）:

| 维度 | 策略 | 示例 |
|-----|------|------|
| **任务类型** | 续写/润色 → 便宜模型<br>大纲/分析 → 强模型 | 续写 100 字用 DeepSeek<br>生成大纲用 GLM-4 |
| **上下文长度** | < 4k token → 便宜模型<br>> 8k token → 必要时用强模型 | 短章用低价<br>长章/复杂剧情用强模型 |
| **用户手动选择** | 提供"模型档位"选择 | 经济版 / 标准版 / 高质量版 |
| **失败降级** | 主模型失败 → 自动切换备用 | DeepSeek 超时 → 尝试通义千问 |

**交付物**:
- [ ] `backend/app/services/model_router.py` 新增路由服务
- [ ] `GenerationService` 集成路由逻辑（生成/续写/改写入口）
- [ ] `ChatService` 集成路由逻辑（对话入口）
- [ ] 章节编辑器增加"模型档位"选择器（可选，默认自动）
- [ ] 模型配置增加"用途标签"（可选：creative / analysis / cheap / balanced）

**验收标准**:
- 默认策略下，续写任务自动选择"低价"模型
- 用户可手动覆盖为"高质量"模型
- 主模型失败时自动降级并记录日志

### Phase 2: 上下文优化（Week 2-3）

#### 2.1 前章摘要分层加载

**目标**: 续写时不加载全部历史摘要，仅加载必要部分

**当前问题**（`generation_service.py`）:
```python
# 可能存在类似逻辑
context = build_context(
    recent_summaries=all_previous_chapter_summaries,  # 全部加载
    ...
)
```

**优化策略**:

| 章节位置 | 加载策略 | 说明 |
|---------|---------|------|
| 最近 5 章 | 完整摘要 | 保持连贯性 |
| 6-20 章 | 压缩摘要（仅 events + unresolved_hooks） | 关键情节与伏笔 |
| 21 章以前 | 仅 unresolved_hooks（未回收伏笔） | 避免遗漏 |
| 角色状态 | 最新快照（合并最近 N 章状态变化） | 不每次重建 |

**交付物**:
- [ ] `backend/app/services/generation_service.py`
  - 重构 `_build_context_bundle` 或相关方法
  - 新增 `load_summaries_layered(outline_id, current_chapter_number)`
- [ ] `backend/app/services/context_service.py`（可选）提取上下文构建逻辑
- [ ] 后端日志记录"上下文 token 节省量"（用于统计）

**验收标准**:
- 第 50 章续写时，输入 token 数相比优化前降低 ≥ 40%
- 连贯性与伏笔追踪功能不受影响（人工抽查 3-5 个案例）
- 结构化摘要（ChapterSummary）字段能正确被分层使用

---

#### 2.2 伏笔与世界观按需过滤

**目标**: 仅加载本章可能相关的伏笔和世界观条目

**当前问题**:
- 所有伏笔（包括已回收的、与本章无关的）可能被加载
- 所有世界观条目被加载，无论本章场景是否相关

**优化策略**:

| 数据 | 过滤策略 | 实现方式 |
|-----|---------|---------|
| **伏笔** | 仅加载 status=open 且（plant_chapter 相关 或 角色匹配 或 关键词匹配） | 基于 `foreshadowing_service` 已有逻辑增强 |
| **世界观** | 按标签/关键词匹配本章场景（POV、地点、时间） | 简单文本匹配或已有 tag 系统 |
| **角色** | 仅加载本章 POV 角色 + 互动角色（而非全部） | 基于 chapter.scenes 或 手动指定 |

**交付物**:
- [ ] `backend/app/services/foreshadowing_service.py` 增强过滤逻辑
- [ ] `backend/app/services/worldview_service.py` 增加按场景过滤方法
- [ ] `GenerationService` 调用过滤后的数据构建上下文
- [ ] 可选配置：关闭过滤（兼容旧行为）

**验收标准**:
- 伏笔加载数量从"全部 open 伏笔"降低到"相关伏笔"
- 世界观加载数量从"全部"降低到"匹配场景的"

### Phase 3: 成本控制与断点续传（Week 3-4）

#### 3.1 成本预估 + 硬限制 + 自动降级

**目标**: 防止大额浪费，提供用户控制

**交付物**:
- [ ] `backend/app/config.py` 补充配置项
  ```python
  MAX_TOKENS_PER_GENERATION: int = 8000  # 硬限制
  MAX_COST_PER_GENERATION: float = 0.5   # 软限制（元）
  AUTO_DOWNGRADE_THRESHOLD: float = 0.2  # 预估超过此值自动用便宜模型
  ```
- [ ] `GenerationService.estimate_cost` 增强
  - 考虑路由后的实际模型单价
  - 返回 `{estimated_cost, estimated_tokens, selected_model, downgrade_applied}`
- [ ] 章节编辑器 CostConfirmModal 增强
  - 显示"预估模型"与"预估费用"
  - 超过硬限制时禁用生成按钮 + 提示
  - 超过软限制时必须确认
- [ ] 用户设置页面（或模型配置）增加全局成本限制配置

**验收标准**:
- 预估费用超过硬限制时无法发起生成
- 预估费用超过软限制时弹窗确认
- 预估超过阈值时自动降级到便宜模型（并在弹窗中提示）

---

#### 3.2 增量生成 + 断点续传

**目标**: 生成中断后可从断点继续，而非全部重来

**实现思路**（利用现有架构）:
1. 流式生成时，定期（每 200-300 token）将已生成内容写入 `Chapter.content_draft`（新增字段）或直接更新 `Chapter.content`
2. 记录当前生成进度（`generation_progress` 字段或临时状态）
3. 中断时标记状态为 `interrupted`
4. 续传时：
   - 从 `content_draft` 读取已生成部分
   - 构造"承接提示词"（"继续以下内容：{last_200_chars}"）
   - 仅生成剩余部分
5. 完成后合并并清理草稿状态

**交付物**:
- [ ] 数据库迁移：`chapters` 表增加字段
  ```sql
  content_draft TEXT
  generation_status VARCHAR  -- 'idle' | 'generating' | 'interrupted'
  generation_checkpoint TEXT  -- JSON: {last_token_count, last_content_snippet, ...}
  ```
- [ ] `backend/app/routers/chapters.py` 增加端点
  - `POST /chapters/{id}/resume` 续传
  - `POST /chapters/{id}/cancel` 取消（可选）
- [ ] `GenerationService` 改造
  - `generate_chapter_stream` 支持 checkpoint 恢复
  - 定期 flush 进度到数据库（注意：单进程场景，DB session 管理）
- [ ] 前端 `ChapterEditor`
  - 检测到 `interrupted` 状态时显示"继续生成"按钮
  - 续传时拼接已有内容 + 新流
  - 取消生成时标记状态

**验收标准**:
- 生成 3000 字中途取消，点击"继续"后仅生成剩余部分
- 最终章节内容完整且连贯
- 费用仅为续传部分（而非全部重来）

**注意事项**:
- 由于架构不改（无持久化队列），中断后若重启 backend，草稿状态会丢失 → 文档中说明此限制
- 仅支持"用户主动取消"和"网络超时"场景，不保证极端情况

---

#### 3.3 结构化输出约束（减少重试）

**目标**: 降低 JSON 解析失败导致的重试

**交付物**:
- [ ] `backend/app/adapters/openai_adapter.py`（及兼容适配器）
  - 支持 `response_format={"type": "json_object"}` 参数（若模型支持）
  - 传递 `json_mode=True` 时自动添加
- [ ] `backend/app/utils/json_extract.py` 增强
  - 增加重试提示词模板（"上次解析失败，错误：{error}，请严格按 JSON 输出"）
  - 限制最大重试次数（默认 2 次，避免无限重试）
- [ ] 服务层（`GenerationService`, `ChatService` 等）调用 JSON 提取时
  - 传递 `json_mode=True`
  - 捕获解析失败，触发带错误信息的重试
- [ ] 日志记录 JSON 解析失败率（用于后续监控）

**验收标准**:
- JSON 提取失败重试率从 15-30% 降至 < 10%
- 超过最大重试次数时返回友好错误（而非静默失败）

- [ ] 前端章节编辑器

#### 4.3 重复计算缓存（简单内存缓存）

**目标**: 避免相同输入的重复 AI 调用

**适用场景**（单进程内存缓存足够）:

| 场景 | 缓存键 | 缓存时长 |
|-----|-------|---------|
| 质量评分 | `hash(chapter.content)` | 24h 或内容变更失效 |
| 一致性检查 | `hash(context + rules)` | 1h |
| 角色关系图 | `project_id + last_updated` | 直到角色变更 |

**交付物**:
- [ ] `backend/app/utils/cache.py` 简单内存缓存工具
  ```python
  @ttl_cache(ttl=3600)
  async def get_quality_score(content: str, model_config) -> QualityScore:
      ...
  ```
- [ ] `QualityService` 应用缓存
- [ ] `ConsistencyService` 应用缓存
- [ ] 管理接口（可选）：`/api/cache/stats` 查看命中率

**验收标准**:
- 相同内容连续评分，第 2 次直接返回缓存结果（日志可观测）
- 内容变更后缓存失效

## 3. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|-----|------|---------|
| 国产模型兼容性差 | 部分功能不可用 | 适配器层做差异化处理，失败时降级到 OpenAI 兼容 |
| 断点续传状态不一致 | 章节内容损坏 | 续传前做快照（写入 version），失败可回退 |
| 上下文分层导致连贯性下降 | 用户体验差 | 提供"关闭分层"开关，默认保守策略（最近 10 章完整） |
| 缓存导致数据不一致 | 评分/检查结果过时 | 缓存键包含版本号或时间戳，内容变更立即失效 |
| 成本统计不准 | 用户困惑 | 明确标注"估算值"，token 计数以实际返回为准 |
